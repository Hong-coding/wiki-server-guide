## 비유로 이해하기

같은 "식당"이라도 두 종류가 있습니다.

- **편의점 도시락 코너(정적)**: 도시락은 새벽에 공장에서 **미리 만들어져** 진열대에 놓여 있습니다. 손님이 오면 직원은 진열대에서 집어 건네기만 합니다. 빠르고, 직원 한 명이 손님 수백 명을 상대할 수 있고, 도시락 맛이 손님마다 다를 일도 없습니다. 대신 "밥 조금만 주세요" 같은 주문은 못 받습니다.
- **주문 즉시 조리하는 식당(동적)**: 손님이 주문할 **때마다** 주방에서 새로 요리합니다. "덜 맵게", "오늘의 메뉴"처럼 손님·시간에 따라 다른 요리를 낼 수 있습니다. 대신 주방(서버 프로그램)이 바쁘고, 재료 창고(데이터베이스)도 관리해야 하며, 주방에 문제가 생기면 손님 전체가 기다립니다.

ts-wiki는 **편의점 도시락 코너**입니다. 도시락 공장이 VitePress 빌드이고, 진열대가 `docs/.vitepress/dist` 폴더, 직원이 nginx나 GitHub Pages입니다.

## 개념 설명

### 응답을 "언제" 만드는가

둘의 차이는 한 문장으로 정리됩니다.

| | 정적(static) | 동적(dynamic) |
|---|---|---|
| 응답 본문을 만드는 때 | **요청 전에 미리**(빌드할 때) | **요청이 올 때마다** |
| 서버가 하는 일 | 파일을 찾아서 그대로 보냄 | 코드를 실행해 응답을 새로 만듦 |
| 같은 주소를 두 번 요청하면 | 똑같은 내용 | 다를 수 있음(시각·로그인 사용자·DB 내용에 따라) |
| 서버에 필요한 것 | 파일 + 파일 서버(nginx 등) | 실행 환경(Node.js·Java 등) + 대개 데이터베이스 |
| 예 | 문서 사이트, 블로그, 회사 소개 페이지 | 쇼핑몰 장바구니, 로그인, 게시판 글쓰기, 은행 |

"정적"이라고 화면이 안 움직이는 것은 아닙니다. 정적 사이트도 JavaScript를 보내서 브라우저 안에서 버튼·검색·애니메이션이 동작할 수 있습니다. **정적·동적은 서버 쪽 이야기**입니다. 서버가 "이미 있는 파일을 보내는가, 그 자리에서 만드는가"의 차이입니다.

### 따라 하기 1: 정적 서버의 응답은 매번 같다

지난 레슨에서 띄운 미리보기 서버(`npx vitepress preview docs --port 5191`)는 빌드 결과물 폴더의 파일을 그대로 보내는 **정적 서버**입니다. 같은 주소에 두 번 요청하고, 내용이 같은지 보여 주는 헤더만 골라 봅니다.

```bash
curl -s -I http://localhost:5191/guide/roadmap
```

1초 간격으로 두 번 요청한 실제 결과에서 관련 줄만 옮기면 다음과 같습니다.

```text
(1번째)
Content-Length: 74249
Last-Modified: Wed, 28 Oct 2026 00:04:18 GMT
ETag: W/"74249-1793145858815"
(2번째)
Content-Length: 74249
Last-Modified: Wed, 28 Oct 2026 00:04:18 GMT
ETag: W/"74249-1793145858815"
```

크기·수정 시각·지문(`ETag`)이 모두 같습니다. `Last-Modified`가 **빌드한 시각**이라는 데 주목합니다. 이 페이지는 요청이 온 지금이 아니라, 빌드할 때 이미 만들어져 있었습니다.

### 따라 하기 2: 동적 서버를 직접 만들기

이번에는 요청이 올 때마다 응답을 새로 만드는 서버를 만듭니다. 실습 폴더(예: `D:\practice\dyn`)를 만들고, 그 안에 `server.mjs` 파일을 다음 내용으로 저장합니다. (`.mjs`는 "최신 JavaScript 모듈 문법으로 쓴 파일"이라는 뜻의 확장자입니다.)

```js
// 요청이 올 때마다 응답을 새로 만드는 아주 작은 동적 서버
import http from 'node:http'

const host = process.env.HOST ?? '127.0.0.1' // 어느 주소로 들어오는 손님을 받을지
const port = 5196 // 몇 번 문에서 기다릴지
let count = 0

const server = http.createServer((req, res) => {
  count += 1
  const now = new Date().toISOString()
  res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' })
  res.end(`<h1>${count}번째 방문입니다</h1><p>서버 시각: ${now}</p>`)
})

server.listen(port, host, () => {
  console.log(`http://${host}:${port} 에서 기다리는 중`)
})
```

한 줄씩 보면 이렇습니다.

- `import http from 'node:http'`: Node.js에 들어 있는 HTTP 서버 기능을 가져옵니다. 따로 설치할 것이 없습니다.
- `http.createServer((req, res) => { ... })`: "요청(`req`)이 올 때마다 이 함수를 실행하라"는 서버를 만듭니다. **이 함수가 주방입니다.**
- `count += 1`, `new Date()`: 요청마다 방문 횟수와 현재 시각이 바뀝니다.
- `res.writeHead(200, ...)`: 상태 코드 `200`과 `Content-Type` 헤더를 정합니다. 지난 레슨에서 `curl -i`로 본 그 줄들을 **내가 직접** 쓰는 것입니다.
- `res.end(...)`: 본문을 보내고 응답을 마칩니다.
- `server.listen(port, host, ...)`: 5196번 창구에서 손님을 기다리기 시작합니다. `host`의 의미는 다음 레슨에서 다룹니다.

실행합니다.

```bash
node server.mjs
```

```text
http://127.0.0.1:5196 에서 기다리는 중
```

새 터미널에서 두 번 요청합니다(Windows는 `curl.exe`).

```bash
curl -s http://127.0.0.1:5196/
curl -s http://127.0.0.1:5196/about
```

실제 출력:

```text
<h1>1번째 방문입니다</h1><p>서버 시각: 2026-10-28T02:11:41.150Z</p>
<h1>2번째 방문입니다</h1><p>서버 시각: 2026-10-28T02:11:42.417Z</p>
```

헤더도 봅니다.

```bash
curl -s -i http://127.0.0.1:5196/
```

```text
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Date: Wed, 28 Oct 2026 02:11:42 GMT
Connection: keep-alive
Keep-Alive: timeout=5
Transfer-Encoding: chunked
```

정적 서버와 비교해 보면 `Last-Modified`도 `ETag`도 없습니다. 응답이 **방금 만들어져서** "언제 바뀐 파일인지"라는 개념이 없기 때문입니다.

**확인 방법**: 요청할 때마다 "N번째 방문"의 숫자와 시각이 바뀌면 성공입니다. `/about`처럼 아무 경로나 넣어도 응답이 나오는 것은 이 서버가 경로(`req.url`)를 전혀 보지 않기 때문입니다. 실습이 끝나면 서버 터미널에서 `Ctrl+C`로 끕니다.

::: tip 브라우저로도 확인
서버를 켠 채 브라우저에서 `http://127.0.0.1:5196`을 열고 새로 고침을 여러 번 해 봅니다. 숫자가 한 번에 2씩 오를 수도 있는데, 브라우저가 페이지와 별도로 아이콘(`/favicon.ico`)도 요청하기 때문입니다. 지난 레슨의 "브라우저는 요청을 여러 번 보낸다"를 직접 확인하는 셈입니다.
:::

### 서버를 껐다 켜면?

동적 서버를 `Ctrl+C`로 끈 뒤 다시 `node server.mjs`로 켜고 요청하면, 숫자가 다시 `1번째`부터 시작합니다. `count`는 **프로그램 메모리에만** 있었기 때문입니다. 실제 동적 서비스는 이런 값을 잃지 않으려고 **데이터베이스**(데이터를 디스크에 안전하게 저장·조회하는 프로그램)를 함께 씁니다. 그래서 동적 서버를 운영하면 "서버 프로그램 + 데이터베이스 + 백업"까지 관리할 것이 늘어납니다.

정적 사이트는 반대로, 서버를 껐다 켜도 진열대의 파일은 그대로입니다. 잃어버릴 상태가 없습니다.

### 장단점 비교

| 기준 | 정적 | 동적 |
|---|---|---|
| 속도 | 파일을 보내기만 하므로 빠름. CDN(전 세계에 복사본을 두는 배달망)에 올리기 쉬움 | 요청마다 코드 실행·DB 조회가 있어 상대적으로 느릴 수 있음 |
| 비용 | GitHub Pages처럼 무료 호스팅이 많음 | 실행 환경이 항상 켜져 있어야 함 |
| 보안 | 서버에서 실행되는 코드가 없어 공격받을 곳이 적음 | 로그인·입력 처리·DB 등 지켜야 할 곳이 많음 |
| 운영 | 파일만 바꿔 넣으면 끝 | 프로세스 감시, 재시작, DB 백업이 필요 |
| 기능 | 사용자마다 다른 내용, 서버 저장, 로그인은 어려움 | 무엇이든 가능 |
| 내용 반영 | **다시 빌드해야** 반영 | 저장 즉시 반영 |

문서·학습 위키처럼 **모든 사람에게 같은 내용을 보여 주고, 글을 쓰는 사람이 적은** 사이트는 정적 방식이 거의 모든 기준에서 유리합니다. 반대로 게시판처럼 **방문자가 글을 쓰는** 사이트는 동적 서버가 필요합니다.

### 중간 지대도 있다

현실의 사이트는 둘을 섞기도 합니다.

- **정적 사이트 + 브라우저 안의 기능**: 서버는 파일만 보내고, 검색·필터·체크리스트는 브라우저에서 JavaScript로 처리합니다. ts-wiki가 이 방식입니다.
- **정적 사이트 + 외부 API**: 화면은 정적 파일이고, 댓글처럼 저장이 필요한 부분만 별도 동적 서버(API)를 부릅니다.
- **동적 서버 앞의 정적 파일 서버**: 동적 서버를 운영할 때도 이미지·CSS·JS 같은 정적 파일은 nginx가 따로 보내게 하는 경우가 많습니다. [리버스 프록시와 HTTPS 개념](../part7-server-learning/04-reverse-proxy)에서 다룹니다.

## ts-wiki에서는

ts-wiki는 정적 사이트입니다. 그 증거와, 그런데도 "동적인 것처럼 보이는" 기능이 어떻게 동작하는지 파일로 확인해 봅니다.

### 증거 1: nginx 상자에는 Node.js가 없다

`Dockerfile`의 두 번째 단계는 이렇습니다.

```dockerfile
FROM nginx:1.27-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/docs/.vitepress/dist /usr/share/nginx/html
EXPOSE 80
```

실제로 서비스하는 상자에는 nginx와 HTML 파일(`dist`)만 들어갑니다. 요청이 와도 실행할 JavaScript 서버 코드가 없습니다. 도시락 진열대와 직원만 있고 주방이 없는 셈입니다.

### 증거 2: 데이터베이스 설정이 없다

`docker-compose.yml` 전체가 이것뿐입니다.

```yaml
services:
  ts-wiki:
    build: .
    container_name: ts-wiki
    ports:
      - "8090:80"
    restart: unless-stopped
```

동적 서비스라면 보통 여기에 데이터베이스 컨테이너가 하나 더 붙습니다. ts-wiki에는 서비스가 `ts-wiki` 하나뿐입니다.

### 그런데 진도 체크는 어떻게 저장되나?

레슨 완료 체크는 서버가 아니라 **브라우저 안에** 저장됩니다. `docs/.vitepress/theme/components/ProgressChecklist.vue`의 2번째 줄 주석이 그대로 말해 줍니다.

```ts
// 레슨별 완료 체크. 진도는 이 브라우저의 localStorage에만 저장됩니다(서버 저장 없음).
```

`localStorage`는 브라우저가 사이트마다 마련해 주는 작은 저장 공간입니다. 그래서 다른 브라우저나 다른 PC에서 열면 체크가 보이지 않습니다. 정적 사이트를 고른 대가이자, 서버에 개인 정보를 저장하지 않는 장점이기도 합니다.

### 검색은 어떻게 하나?

`config.mts`의 검색 설정은 `provider: 'local'`입니다.

```ts
    search: {
      provider: 'local',
```

빌드할 때 모든 페이지의 글을 모아 **검색 색인 파일**을 미리 만들어 `dist/assets/chunks/` 아래에 넣어 둡니다(작성 시점 빌드에서는 `@localSearchIndexroot.-0CvXqQm.js` 같은 이름). 브라우저는 그 파일을 받아 **브라우저 안에서** 검색합니다. 검색 요청이 서버로 가지 않습니다. 같은 파일의 31번째 줄 주석 "로컬 검색 인덱스가 한 청크에 들어가 500kB를 넘으므로 경고 기준만 올립니다."가 이 색인이 꽤 크다는 것을 알려 줍니다.

### "마지막 수정" 시각은?

각 페이지의 "마지막 수정" 시각(`lastUpdated: true`)도 요청할 때가 아니라 **빌드할 때** Git 이력에서 읽어 HTML에 적어 둡니다. 그래서 `.github/workflows/deploy.yml`의 24번째 줄에 이런 설정이 있습니다.

```yaml
          fetch-depth: 0 # lastUpdated(마지막 수정 시각) 표시에 git 이력이 필요합니다.
```

빌드하는 순간 필요한 정보를 모두 모아 두는 것, 이것이 정적 사이트의 방식입니다. 자세한 원리는 [정적 사이트 생성기(SSG)와 빌드](./05-ssg)에서 다룹니다.

## 자주 하는 실수

### 1. 문서를 고쳤는데 사이트가 그대로다

- **증상**: 마크다운을 고치고 nginx 컨테이너(`localhost:8090`)를 새로 고쳤는데 옛날 내용이 나옵니다.
- **원인**: 정적 사이트는 **빌드할 때** 내용이 정해집니다. 진열대의 도시락은 공장에서 새로 만들어 와야 바뀝니다.
- **해결**: 다시 빌드합니다. Docker라면 `docker compose up -d --build`, GitHub Pages라면 push 후 Actions가 끝나기를 기다립니다.

### 2. 정적 사이트에 "글쓰기 기능"을 넣으려 한다

- **증상**: 위키 화면에서 바로 글을 저장하는 버튼을 만들었는데, 새로 고치면 사라지거나 내 브라우저에만 보입니다.
- **원인**: 정적 서버는 받은 내용을 저장할 곳(주방·창고)이 없습니다. `localStorage`에 저장했다면 그 브라우저에만 남습니다.
- **해결**: ts-wiki처럼 "글은 Git으로 고치고 push한다"는 흐름을 쓰거나, 저장이 꼭 필요하면 별도 동적 서버(API)와 데이터베이스를 둡니다. [Express로 웹 서버 만들기](../part7-server-learning/03-express)에서 동적 서버를 만들어 봅니다.

### 3. 동적 서버를 켠 채로 잊는다

- **증상**: 다음 실습에서 `node server.mjs`를 실행했더니 `Error: listen EADDRINUSE: address already in use 127.0.0.1:5196`이 나옵니다.
- **원인**: 앞에서 켠 서버가 다른 터미널에서 여전히 5196번 창구를 차지하고 있습니다.
- **해결**: 그 터미널을 찾아 `Ctrl+C`로 끕니다. 어느 터미널인지 모르겠다면 [다음 레슨](./03-localhost-port-host)의 "포트를 쓰는 프로그램 찾기"를 씁니다.

### 4. "정적 = 움직임 없는 화면"이라고 생각한다

- **증상**: "ts-wiki는 다크 모드도 되고 검색도 되니까 동적 사이트"라고 설명합니다.
- **원인**: 정적·동적은 **서버가 응답을 언제 만드는가**의 구분입니다. 브라우저 안에서 JavaScript가 움직이는 것과는 별개입니다.
- **해결**: "서버가 파일을 그대로 보내는가?"로 판단합니다. ts-wiki의 nginx는 파일을 그대로 보내므로 정적입니다.

### 과제 2 ⭐ 동적 서버 껐다 켜기

`server.mjs`를 실행해 세 번 요청한 뒤, `Ctrl+C`로 끄고 다시 켜서 한 번 더 요청합니다. 숫자가 어떻게 되나요?

::: details 정답 보기
다시 `1번째 방문입니다`부터 시작합니다. `count`는 메모리에만 있었고, 프로그램이 끝나면서 사라졌기 때문입니다. 값을 계속 유지하려면 파일이나 데이터베이스에 저장해야 합니다.
:::

### 과제 3 ⭐⭐ 경로에 따라 다른 응답

`server.mjs`를 고쳐 `/menu`로 요청하면 `<h1>아메리카노 3,000원</h1>`을, 그 밖의 경로는 지금처럼 방문 횟수를 보여 주게 만들어 봅니다.

::: details 정답 보기
`createServer` 안의 함수를 이렇게 바꿉니다.

```js
const server = http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' })
  // 요청 경로(req.url)에 따라 다른 응답을 만듭니다.
  if (req.url === '/menu') {
    res.end('<h1>아메리카노 3,000원</h1>')
    return
  }
  count += 1
  res.end(`<h1>${count}번째 방문입니다</h1>`)
})
```

서버를 다시 켠 뒤 `curl -s http://127.0.0.1:5196/menu`로 확인합니다. 동적 서버는 요청 정보(경로·헤더 등)를 보고 응답을 자유롭게 바꿀 수 있습니다.
:::

### 과제 4 ⭐⭐⭐ 404도 직접 만들기

과제 3에 이어, `/`와 `/menu`가 아닌 경로에는 상태 코드 `404`와 "없는 페이지입니다"를 보내도록 고치고 `curl -i`로 확인해 봅니다.

::: details 정답 보기
```js
const server = http.createServer((req, res) => {
  if (req.url === '/menu') {
    res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' })
    res.end('<h1>아메리카노 3,000원</h1>')
    return
  }
  if (req.url === '/') {
    count += 1
    res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' })
    res.end(`<h1>${count}번째 방문입니다</h1>`)
    return
  }
  // 그 밖의 경로는 404로 응답합니다.
  res.writeHead(404, { 'Content-Type': 'text/html; charset=utf-8' })
  res.end('<h1>없는 페이지입니다</h1>')
})
```

`curl -i http://127.0.0.1:5196/nope`의 첫 줄이 `HTTP/1.1 404 Not Found`면 성공입니다. nginx의 `try_files ... =404`가 하는 일을 직접 코드로 짠 것입니다.
:::

## 확인 퀴즈

1. 정적 사이트와 동적 서버를 가르는 기준은 무엇인가요?
2. 같은 주소를 두 번 요청했을 때 정적 서버의 `ETag`는 어떤가요?
3. ts-wiki의 진도 체크는 어디에 저장되나요?
4. ts-wiki의 검색은 서버에 요청을 보내나요?
5. 정적 사이트의 내용을 바꾸려면 무엇을 다시 해야 하나요?

::: details 정답 보기
1. 응답 본문을 **언제** 만드는가입니다. 정적은 요청 전(빌드 때), 동적은 요청이 올 때마다 만듭니다.
2. 같습니다. 파일이 바뀌지 않았기 때문입니다.
3. 브라우저의 `localStorage`입니다. 서버에는 저장하지 않습니다.
4. 아닙니다. 빌드 때 만든 검색 색인 파일을 받아 브라우저 안에서 검색합니다.
5. 빌드입니다.
:::

## 정리

- **정적**: 응답을 빌드할 때 미리 만들어 두고, 서버는 파일을 그대로 보냅니다. **동적**: 요청이 올 때마다 코드를 실행해 응답을 만듭니다.
- Node.js의 `http.createServer` 몇 줄로 동적 서버를 만들 수 있고, 상태 코드·헤더·본문을 직접 정합니다.
- 정적은 빠르고 싸고 안전하고 운영이 쉬운 대신, 사용자별 내용·서버 저장이 어렵고 바꾸려면 다시 빌드해야 합니다.
- ts-wiki는 정적 사이트입니다. nginx 상자에는 HTML만 있고, 진도는 `localStorage`, 검색은 빌드 때 만든 색인으로 브라우저 안에서 처리합니다.
- "정적 = 움직임 없는 화면"이 아닙니다. 정적·동적은 서버 쪽 구분입니다.
