# 왜 Markdown으로 쓰나

## 이번에 배울 것

- 글 형식 세 가지(Markdown, HTML, 위지윅 편집기 + DB)의 차이를 저장 방식 기준으로 설명할 수 있다.
- `git diff`로 Markdown 변경을 읽고, 왜 리뷰가 쉬운지 말할 수 있다.
- "이식성"(다른 도구로 옮기기 쉬운 정도)이 왜 장기 운영에 중요한지 말할 수 있다.
- ts-wiki가 줄바꿈을 LF로 고정한 이유를 git diff와 연결해 설명할 수 있다.

## 먼저 알아 둘 것

- [왜 VitePress인가](./02-why-vitepress)
- git이 "파일의 변경 이력을 저장하는 도구"라는 것 정도만 알면 됩니다. 설치는 [준비물 설치](../part0-start/03-setup)에서 했습니다.

## 비유로 이해하기

메뉴판 원고를 보관하는 방법을 세 가지로 생각해 봅시다.

- **Markdown**: 원고를 **메모장 글**로 씁니다. "제목은 # 표시, 표는 | 로 칸 나누기" 같은 간단한 약속만 있습니다. 누가 어느 글자를 고쳤는지 빨간 펜으로 비교하기 쉽습니다.
- **HTML**: 원고를 **인쇄소 조판 지시서**로 씁니다. "여기서 표 시작, 여기서 줄 시작, 여기서 칸 시작…" 지시가 글보다 많습니다. 비교는 되지만 지시문 사이에서 글을 찾아야 합니다.
- **위지윅 + DB**: 원고를 **매장 디지털 화면 속에서 바로** 고칩니다. 편하지만 원고 파일이 손에 없습니다. 화면 회사의 창고(데이터베이스)에 있습니다.

ts-wiki는 "한 사람이 오래 관리하고, 필요하면 다른 도구로 옮길 수 있어야 한다"는 조건 때문에 메모장 글(Markdown)을 골랐습니다.

## 개념 설명

### 1. 요구사항: 글 형식에 무엇이 필요했나

| 요구사항 | 글 형식에 대한 질문 |
|---|---|
| 2. 코드 예제 많음 | 코드 블록을 쉽게 쓸 수 있나? 언어 표시가 되나? |
| 5. 한 사람이 관리 | 변경 이력을 남기고, 실수를 되돌릴 수 있나? |
| 3·4. 공개 + 사내 서버 | 같은 원본으로 여러 곳에 올릴 수 있나? |
| (숨은 요구사항) 오래 운영 | 도구를 바꿔야 할 때 글을 그대로 가져갈 수 있나? |

### 2. 세 가지 형식 한눈에 보기

같은 내용("한빛 카페 메뉴" 표)을 세 형식으로 쓰면 이렇습니다.

**Markdown** (`menu.md`, 105바이트)

```md
# 한빛 카페 메뉴

| 메뉴 | 가격 |
|---|---|
| 아메리카노 | 4000 |
| 카페라테 | 4500 |
```

**HTML** (`menu.html`, 224바이트)

```html
<h1>한빛 카페 메뉴</h1>
<table>
  <thead><tr><th>메뉴</th><th>가격</th></tr></thead>
  <tbody>
    <tr><td>아메리카노</td><td>4000</td></tr>
    <tr><td>카페라테</td><td>4500</td></tr>
  </tbody>
</table>
```

**위지윅 + DB**: 파일이 없습니다. 편집 화면에서 표를 그리면 그 내용이 데이터베이스의 어느 표(테이블) 한 칸에 저장됩니다. 저장 형식은 도구마다 다릅니다.

바이트 수(파일 크기)만 봐도 HTML은 같은 내용에 두 배 넘게 필요합니다. 늘어난 부분은 전부 "지시문(태그)"입니다.

### 3. 따라 하기: git diff로 변경 비교하기

**diff**(차이)는 "두 버전에서 무엇이 바뀌었나"를 줄 단위로 보여 주는 결과입니다. 리뷰(review, 다른 사람이나 미래의 내가 변경을 검토하는 일)는 대부분 diff를 읽는 일입니다.

실습 폴더를 만듭니다.

```powershell
# Windows PowerShell
mkdir $HOME\md-diff
cd $HOME\md-diff
git init -b main
```

```bash
# macOS / Linux
mkdir -p ~/md-diff && cd ~/md-diff
git init -b main
```

위의 `menu.md`, `menu.html` 두 파일을 VS Code로 만들어 저장한 뒤 첫 커밋을 합니다. (git을 처음 쓰면 커밋 전에 `git config user.name`, `git config user.email`로 이름과 메일을 한 번 등록해야 합니다.)

```bash
git add .
git commit -m "docs: 메뉴 추가"
```

이제 **카페라테 가격을 4500에서 4800으로** 두 파일 모두 고치고 diff를 봅니다.

```bash
git diff menu.md
```

실제 출력:

```text
diff --git a/menu.md b/menu.md
index 111ff96..8d725bd 100644
--- a/menu.md
+++ b/menu.md
@@ -3,4 +3,4 @@
 | 메뉴 | 가격 |
 |---|---|
 | 아메리카노 | 4000 |
-| 카페라테 | 4500 |
+| 카페라테 | 4800 |
```

**해설**

- `-`로 시작하는 줄은 지워진 줄, `+`로 시작하는 줄은 새로 생긴 줄입니다.
- `@@ -3,4 +3,4 @@`는 "원래 파일 3번째 줄부터 4줄, 새 파일 3번째 줄부터 4줄을 보여 준다"는 위치 정보입니다.
- 앞에 공백이 있는 줄은 바뀌지 않은 주변 줄(문맥)입니다.
- `index 111ff96..8d725bd`의 값은 파일 내용마다 달라지므로 여러분 화면과 다를 수 있습니다.

```bash
git diff menu.html
```

```text
...
@@ -3,6 +3,6 @@
   <thead><tr><th>메뉴</th><th>가격</th></tr></thead>
   <tbody>
     <tr><td>아메리카노</td><td>4000</td></tr>
-    <tr><td>카페라테</td><td>4500</td></tr>
+    <tr><td>카페라테</td><td>4800</td></tr>
   </tbody>
 </table>
```

HTML도 diff가 되긴 합니다. 하지만 바뀐 숫자를 찾으려면 태그 사이를 눈으로 훑어야 합니다. 문서가 길어지고 태그가 중첩될수록 이 차이는 커집니다.

한 줄 안에서 **어느 단어가** 바뀌었는지만 보고 싶으면 `--word-diff`를 씁니다.

```bash
git diff --word-diff menu.md
```

```text
...
| 카페라테 | [-4500-]{+4800+} |
```

`[-...-]`는 지운 단어, `{+...+}`는 넣은 단어입니다. Markdown은 지시문이 거의 없어서 단어 단위 비교가 특히 깔끔합니다.

**확인 방법**: `git diff --stat`을 실행해 두 파일이 각각 `2 +-`(1줄 추가, 1줄 삭제)로 나오면 성공입니다.

```text
 menu.html | 2 +-
 menu.md   | 2 +-
 2 files changed, 2 insertions(+), 2 deletions(-)
```

위지윅 + DB 방식에서는 이 실습 자체를 할 수 없습니다. 비교할 파일이 git에 없기 때문입니다. 도구가 자체 "편집 이력" 화면을 제공하는 경우가 많지만, 그 이력은 그 도구 안에서만 볼 수 있습니다.

실습이 끝나면 폴더를 지웁니다.

```powershell
cd $HOME; Remove-Item -Recurse -Force $HOME\md-diff
```

```bash
cd ~ && rm -rf ~/md-diff
```

### 4. 이식성: 도구를 바꿀 때

**이식성**(portability)은 "다른 환경·도구로 옮기기 쉬운 정도"입니다. 위키는 몇 년씩 운영하므로 그 사이에 도구가 바뀔 확률이 높습니다. 실제로 [2-1](./01-wiki-tools-compare)에서 본 것처럼, 작성 시점에 유명 테마 하나가 유지보수 종료 일정을 공지하기도 했습니다.

| 형식 | 다른 SSG로 옮길 때 | 다른 위키·서비스로 옮길 때 |
|---|---|---|
| Markdown | VitePress·Docusaurus·MkDocs 모두 Markdown을 읽습니다. 파일을 복사하고 도구 전용 문법(컴포넌트, 컨테이너 등)만 고칩니다. | 많은 위키·서비스가 Markdown 가져오기(import)를 지원합니다(지원 범위는 각 공식 문서 확인). |
| HTML | 다시 Markdown으로 바꾸거나 HTML 그대로 써야 합니다. 공통 레이아웃이 페이지마다 박혀 있으면 걷어 내야 합니다. | HTML 가져오기를 지원하는 곳이 있지만 결과가 들쭉날쭉합니다. |
| 위지윅 + DB | 먼저 도구의 **내보내기 기능**으로 파일을 꺼내야 합니다. 형식은 도구가 정합니다. | 내보내기 → 변환 → 가져오기. 표·이미지·내부 링크가 깨지기 쉽습니다. |

::: info Markdown에도 "방언"이 있습니다
Markdown은 여러 갈래로 발전해서, 기본 규격인 **CommonMark**와 GitHub이 확장한 **GFM**(GitHub Flavored Markdown, 표·체크박스 등 추가)이 있습니다. VitePress의 `::: tip` 같은 컨테이너나 `LessonMeta` 같은 Vue 컴포넌트는 **VitePress 전용**이라, 다른 도구로 옮길 때 이 부분만 고쳐야 합니다. 전용 문법을 적게 쓸수록 이식성이 높아집니다.
:::

### 5. 후보 비교표

| 형식 | 장점 | 단점 | 어울리는 상황 |
|---|---|---|---|
| Markdown | 메모장으로 편집, git diff가 깔끔, 리뷰 쉬움, 여러 도구가 읽음, 코드 블록 쓰기 쉬움 | 문법을 조금 배워야 함, 복잡한 레이아웃은 어려움, 미리보기를 따로 봐야 함 | 개발자가 쓰는 기술 문서, 코드 예제가 많은 위키 |
| HTML | 어떤 레이아웃이든 가능, 브라우저가 바로 읽음 | 글보다 태그가 많음, 공통 부분 반복, diff 읽기 어려움 | 디자인이 중요한 한두 장짜리 페이지 |
| 위지윅 + DB | 문법 몰라도 됨, 보이는 그대로 편집, 여러 명 동시 편집 | git 리뷰 불가, 도구에 묶임, 백업은 DB 단위 | 개발자가 아닌 사람들이 함께 쓰는 문서 |

## ts-wiki에서는

### 모든 글이 `docs/` 아래 Markdown 파일

ts-wiki의 `README.md` 첫 문단에 이 결정이 적혀 있습니다.

```text
[VitePress](https://vitepress.dev/) 기반이며 모든 문서는 `docs/` 아래 마크다운 파일입니다.
```

글이 파일이므로 GitHub에서 그대로 보이고, 고치고, 리뷰할 수 있습니다. `config.mts`의 `editLink` 설정이 그 흐름을 화면에 연결합니다.

```ts
    editLink: {
      pattern: 'https://github.com/Hong-coding/ts-wiki/edit/main/docs/:path',
      text: 'GitHub에서 이 페이지 고치기',
    },
```

위키 각 페이지 아래의 "GitHub에서 이 페이지 고치기" 링크를 누르면 GitHub의 Markdown 편집 화면이 열립니다. `:path`에는 그 페이지의 파일 경로가 들어갑니다. 글이 DB에 있었다면 이런 연결은 만들 수 없습니다.

### 줄바꿈을 LF로 고정: `.gitattributes`

ts-wiki의 `.gitattributes`는 세 줄입니다.

```text
* text=auto eol=lf
*.png binary
*.jpg binary
```

- 첫 줄은 "텍스트 파일은 저장소에 LF 줄바꿈으로 저장하고, 작업 폴더에도 LF로 꺼낸다"는 뜻입니다.
- **줄바꿈 문자**는 Windows가 CRLF(두 글자), macOS·Linux가 LF(한 글자)를 주로 씁니다. 눈에는 안 보이지만 diff는 이 차이를 "줄이 바뀌었다"고 봅니다.
- 실습 폴더에서 6줄짜리 `menu.md`의 줄바꿈만 CRLF로 바꾸고 `git diff --stat`을 보니, 내용은 그대로인데 **모든 줄이 바뀐 것**으로 나왔습니다.

```text
 menu.md | 12 ++++++------
 1 file changed, 6 insertions(+), 6 deletions(-)
```

Markdown을 고른 이유가 "diff가 깔끔해서"인데, 줄바꿈이 섞이면 그 장점이 사라집니다. 그래서 `.gitattributes`로 막아 둔 것입니다. `*.png binary`는 이미지 파일을 텍스트로 착각해 줄바꿈을 바꾸지 말라는 뜻입니다.

### 작성 규칙과 Markdown

ts-wiki의 `docs/guide/writing-guide.md`는 모든 레슨이 같은 뼈대(이번에 배울 것 → 개념 설명 → 자주 하는 실수 → …)를 따르도록 정합니다. Markdown은 형식이 자유로운 만큼, 규칙이 없으면 파일마다 모양이 달라집니다. **형식이 단순한 대신 규칙으로 일관성을 지킨다**는 것이 ts-wiki의 선택입니다.

### ts-wiki의 결정과 그 대가

| 얻은 것 | 내준 것(대가) |
|---|---|
| git으로 모든 변경 이력·되돌리기·리뷰 | 글을 쓰려면 에디터와 git을 익혀야 함 |
| 같은 파일로 GitHub Pages와 사내 서버 둘 다 | 웹 화면에서 바로 고칠 수 없음(GitHub 편집 화면으로 대신) |
| 다른 SSG로 옮기기 쉬움 | VitePress 전용 문법(컨테이너, 컴포넌트)은 옮길 때 고쳐야 함 |
| 코드 블록을 백틱 세 개로 간단히 | 꺾쇠·중괄호 작성 규칙을 지켜야 함([2-2](./02-why-vitepress) 참고) |

## 이럴 땐 다른 걸 고르세요

- **글 쓰는 사람이 git을 쓰지 않는 직군(영업·운영·매장 직원)** → 위지윅 편집기가 있는 위키나 SaaS가 낫습니다. 교육 비용이 diff의 장점보다 큽니다.
- **디자인이 핵심인 랜딩 페이지 한두 장** → HTML(또는 화면 제작 도구)이 더 자유롭습니다.
- **조직에 정해진 문서 결재 시스템이 있다** → Markdown + git의 리뷰 흐름(Pull Request)도 강력하지만, 조직의 공식 절차가 있다면 그쪽을 따르는 것이 맞습니다.

## 자주 하는 실수

### 실수 1: 내용은 그대로인데 diff가 파일 전체

- **증상**: 한 글자 고쳤는데 `git diff`가 모든 줄을 `-`/`+`로 보여 줍니다.
- **원인**: 에디터나 설정 때문에 줄바꿈이 CRLF와 LF 사이에서 바뀌었습니다.
- **해결**: 저장소에 `.gitattributes`(`* text=auto eol=lf`)를 두고, VS Code 오른쪽 아래 상태 표시줄의 `CRLF`를 눌러 `LF`로 바꿉니다.

### 실수 2: 표가 깨져서 글자 그대로 나옴

- **증상**: 화면에 표 대신 `| 메뉴 | 가격 |` 글자가 그대로 보입니다.
- **원인**: 머리글 아래 구분 줄(`|---|---|`)을 빼먹었거나, 표 바로 위에 빈 줄이 없습니다.
- **해결**: 표 위에 빈 줄을 두고, 머리글 다음 줄에 구분 줄을 넣습니다. 칸 안에 `|` 글자를 써야 하면 `\|`로 씁니다.

### 실수 3: 코드 블록이 끝나지 않음

- **증상**: 어느 지점부터 페이지 끝까지 전부 코드 블록 배경으로 보입니다.
- **원인**: 백틱 세 개로 연 코드 블록을 닫지 않았습니다.
- **해결**: 여는 줄과 닫는 줄의 백틱 개수가 같은지 확인합니다. 코드 블록 안에 백틱 세 개를 보여 줘야 하면 바깥을 백틱 네 개로 엽니다.

### 실수 4: 위지윅에서 복사해 붙인 글이 이상함

- **증상**: 다른 문서 편집기에서 복사해 붙였더니 `**`가 남거나 표가 사라집니다.
- **원인**: 위지윅 편집기의 서식이 Markdown 문법과 1:1로 맞지 않습니다.
- **해결**: 붙여 넣은 뒤 VS Code 미리보기(Ctrl+Shift+V)나 개발 서버 화면으로 반드시 확인합니다.

## 직접 해 보기

### 과제 1 ⭐ 형식 바꿔 쓰기

다음 HTML을 Markdown으로 바꿔 보세요.

```html
<h2>영업시간</h2>
<ul>
  <li>평일 08:00~20:00</li>
  <li>주말 10:00~18:00</li>
</ul>
```

::: details 정답 보기
```md
## 영업시간

- 평일 08:00~20:00
- 주말 10:00~18:00
```
:::

### 과제 2 ⭐⭐ word-diff 읽기

3절 실습 폴더에서 `menu.md`에 "바닐라라테 | 5000" 줄을 추가하고, 아메리카노 가격을 4200으로 바꾼 뒤 `git diff`와 `git diff --word-diff`를 비교하세요. 어떤 경우에 `--word-diff`가 더 읽기 쉬운가요?

::: details 힌트
- 줄이 통째로 추가된 경우(바닐라라테)는 두 방식이 비슷합니다.
- 한 줄 안에서 일부만 바뀐 경우(4000 → 4200)는 `--word-diff`가 `[-4000-]{+4200+}`처럼 바뀐 단어만 짚어 줘서 더 읽기 쉽습니다.
:::

### 과제 3 ⭐⭐ CRLF 함정 재현

실습 폴더에서 VS Code로 `menu.md`를 열고, 오른쪽 아래 `LF`를 `CRLF`로 바꿔 저장한 뒤 `git diff --stat`을 보세요. 그다음 `.gitattributes` 파일을 만들어 `* text=auto eol=lf`를 넣고 `git add --renormalize .`를 실행한 뒤 다시 `git status`를 확인합니다.

::: details 힌트
CRLF로 바꾸면 내용이 같아도 모든 줄이 바뀐 것으로 나옵니다. `.gitattributes`를 두고 `git add --renormalize .`를 하면 저장소에는 LF로 들어가므로 줄바꿈만 바뀐 변경은 사라지고, 새로 만든 `.gitattributes`만 변경으로 남습니다. PC의 `core.autocrlf` 설정에 따라 결과가 조금 다를 수 있으니, 다르면 `git config core.autocrlf`로 설정값을 확인해 보세요.
:::

### 과제 4 ⭐⭐⭐ 이식성 점검

ts-wiki의 레슨 파일 하나를 골라(읽기만), **VitePress 전용 문법**을 모두 찾아 목록으로 만들어 보세요. 이 파일을 MkDocs로 옮긴다면 고쳐야 할 부분입니다.

::: details 힌트
찾을 것: frontmatter(`---`로 둘러싼 머리말), `LessonMeta` 같은 Vue 컴포넌트 태그, `::: tip`/`::: details` 같은 컨테이너, `:minutes`처럼 콜론으로 시작하는 Vue 속성. 표·목록·코드 블록·링크는 대부분의 도구가 그대로 읽습니다.
:::

## 확인 퀴즈

1. `git diff` 출력에서 `-`, `+`, 공백으로 시작하는 줄은 각각 무엇인가요?
2. 위지윅 + DB 방식에서 git 리뷰가 어려운 이유는?
3. ts-wiki가 `.gitattributes`에 `eol=lf`를 둔 이유를 "Markdown을 고른 이유"와 연결해 설명하세요.
4. Markdown 파일을 다른 SSG로 옮길 때 주로 고쳐야 하는 부분은?

::: details 정답 보기
1. `-`는 지워진 줄, `+`는 추가된 줄, 공백은 바뀌지 않은 주변 줄(문맥)입니다.
2. 글이 파일이 아니라 데이터베이스에 저장되어 git이 변경을 추적할 대상이 없기 때문입니다.
3. Markdown을 고른 큰 이유가 diff가 깔끔하다는 것인데, 줄바꿈 문자가 CRLF와 LF로 섞이면 내용이 같아도 모든 줄이 바뀐 것으로 보여 리뷰가 어려워집니다. 그래서 LF로 고정했습니다.
4. 도구 전용 문법입니다. VitePress라면 `:::` 컨테이너, Vue 컴포넌트 태그, frontmatter 항목 등입니다.
:::

## 정리

- 글 형식은 **Markdown(텍스트 파일) / HTML(태그가 많은 파일) / 위지윅 + DB(파일 없음)** 로 나눠 볼 수 있습니다.
- Markdown은 `git diff`가 깔끔해서 변경 리뷰와 되돌리기가 쉽습니다.
- Markdown은 여러 도구가 읽으므로 **이식성**이 높습니다. 도구 전용 문법만 줄이면 됩니다.
- ts-wiki는 모든 글을 `docs/` 아래 Markdown으로 두고, `editLink`로 GitHub 편집 화면과 연결했습니다.
- `.gitattributes`의 `eol=lf`는 줄바꿈 때문에 diff가 망가지는 것을 막습니다.
- 대가는 "git과 문법을 배워야 한다"는 것이고, 비개발자가 주로 쓴다면 위지윅이 더 낫습니다.
