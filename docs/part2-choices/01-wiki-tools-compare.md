## 비유로 이해하기

동네 카페 "한빛 카페"가 메뉴판을 만든다고 해 봅시다. 방법은 여러 가지입니다.

| 방법 | 카페 비유 | 위키 도구 |
|---|---|---|
| 인쇄소에 원고를 맡겨 메뉴판을 **미리 찍어 두기** | 원고(글)만 고쳐 다시 찍으면 됩니다. 손님은 찍힌 종이를 봅니다. | 정적 사이트 생성기(VitePress·Docusaurus·MkDocs) |
| 매장에 **디지털 메뉴 화면과 관리 컴퓨터**를 두기 | 직원이 화면에서 바로 고칩니다. 대신 컴퓨터가 꺼지면 메뉴도 꺼집니다. | 동적 위키(Wiki.js) |
| **배달 앱에 메뉴 등록** | 화면은 앱 회사가 다 만들어 줍니다. 대신 앱 회사의 규칙·요금을 따라야 합니다. | SaaS(GitBook·Notion) |
| **손으로 한 장씩 그리기** | 도구가 필요 없지만, 메뉴가 50개면 50장을 다 다시 그려야 합니다. | 정적 HTML 직접 작성 |

어느 방법이 "제일 좋다"는 없습니다. 메뉴가 몇 개인지, 누가 고치는지, 매장 밖에서도 보여야 하는지에 따라 답이 달라집니다. 이 레슨은 그 "따라 달라지는 기준"을 표로 정리합니다.

## 개념 설명

### 1단계: 요구사항을 다시 적기

비교는 항상 **요구사항부터** 시작합니다. 도구부터 보면 "기능이 많은 것"이 좋아 보이는데, 쓰지 않는 기능은 관리할 짐일 뿐입니다. ts-wiki의 요구사항을 비교하기 좋은 질문으로 바꾸면 다음과 같습니다.

| 요구사항 | 도구에게 던지는 질문 |
|---|---|
| 1. 초보자 학습 위키 | 사이드바·이전/다음 버튼·목차가 기본으로 있나? |
| 2. 코드 예제 많음 | 코드 하이라이트·줄 번호가 기본으로 되나? 코드 안의 특수 문자 때문에 깨지지 않나? |
| 3. 무료 공개 | 돈 없이 인터넷에 띄울 수 있나? |
| 4. 사내 서버에도 | 인터넷이 막힌 서버에서 혼자 돌아가나? |
| 5. 한 사람이 관리 | 데이터베이스·로그인·백업처럼 돌봐야 할 부품이 몇 개인가? |
| 6. 검색 | 외부 서비스 없이 검색이 되나? |
| 7. 다크 모드 | 기본 테마에 다크 모드 전환이 있나? |

### 2단계: 후보를 네 갈래로 나누기

후보 여섯 개를 먼저 성격별로 묶으면 비교가 훨씬 쉬워집니다.

```text
[A] 정적 사이트 생성기(SSG)  ─ 마크다운 → 빌드 → HTML 파일 묶음
     VitePress(Vue)   Docusaurus(React)   MkDocs Material(Python)

[B] 동적 위키               ─ 서버 프로그램 + 데이터베이스가 계속 돌아감
     Wiki.js

[C] SaaS(서비스형 소프트웨어) ─ 남의 서버에 가입해서 씀, 설치 없음
     GitBook   Notion

[D] 도구 없이 직접           ─ HTML 파일을 손으로 작성
     정적 HTML
```

- **SSG(Static Site Generator, 정적 사이트 생성기)**: 글을 미리 HTML 파일로 바꿔 두는 프로그램입니다. 결과물은 그냥 파일이라 아무 웹 서버(nginx 등)나 GitHub Pages에 올리면 됩니다.
- **동적 위키**: 방문자가 페이지를 열 때마다 서버 프로그램이 데이터베이스(DB, 데이터를 저장·검색하는 전용 프로그램)에서 글을 꺼내 화면을 만듭니다. 웹 화면에서 바로 글을 고칠 수 있습니다.
- **SaaS**(Software as a Service): 프로그램을 설치하지 않고 회사가 운영하는 웹 서비스에 가입해서 씁니다.

요구사항 3번(무료 공개)·4번(사내 서버)·5번(한 사람 관리)을 놓고 보면 갈래마다 성격이 뚜렷합니다.

| 갈래 | 무료 공개 | 사내 서버 | 관리 부품 |
|---|---|---|---|
| A. SSG | GitHub Pages 같은 무료 정적 호스팅에 올릴 수 있음 | 빌드된 파일을 nginx로 서비스하면 끝 | 적음(빌드 도구 하나) |
| B. 동적 위키 | 서버를 계속 켜 둘 곳이 필요(대개 유료 서버나 사내 서버) | 가능 | 많음(앱 + DB + 백업 + 계정) |
| C. SaaS | 요금제에 따라 다름 | 사내망 전용 설치는 대개 불가(서비스 회사 서버에 있음) | 거의 없음(대신 회사 정책에 의존) |
| D. 직접 HTML | 가능 | 가능 | 도구는 없지만 페이지마다 손이 많이 감 |

### 3단계: 후보 하나씩 살펴보기

아래 내용은 **각 도구의 공식 문서 기준**입니다. 버전은 작성 시점(2026-10)에 npm·PyPI에서 확인한 값이며, 요금은 바뀌기 쉬우므로 **작성 시점 기준, 공식 페이지에서 확인**하세요.

#### VitePress

- Vue 팀이 만든 SSG입니다. 이름처럼 **Vite**(빠른 개발 서버·빌드 도구) 위에서 동작합니다.
- 글은 Markdown으로 쓰고, 필요하면 그 안에 **Vue 컴포넌트**(화면 부품)를 넣을 수 있습니다.
- 기본 테마에 사이드바·목차·이전/다음 링크·다크 모드가 있고, 설정 한 줄로 **브라우저 안에서 동작하는 로컬 검색**(MiniSearch 사용)을 켤 수 있습니다.
- 작성 시점 npm 최신 안정판은 1.6.4이고, 2.0은 알파(alpha, 정식 전 시험판) 단계입니다. ts-wiki는 1.6.3을 고정해 씁니다.

#### Docusaurus

- Meta(구 Facebook)가 공개한 SSG입니다. **React**(Meta가 만든 화면 라이브러리) 기반이고, 글은 Markdown 또는 **MDX**(Markdown 안에 React 컴포넌트를 쓰는 형식)로 씁니다.
- **문서 버전 관리**(v1 문서, v2 문서를 따로 유지)와 다국어(i18n) 기능이 기본으로 있습니다. 제품 문서에 많이 쓰이는 이유입니다.
- 검색은 공식 문서가 **Algolia DocSearch**(외부 검색 서비스) 연동을 1순위로 안내합니다. 외부 서비스 없이 쓰는 로컬 검색은 커뮤니티 플러그인으로 붙입니다.
- 작성 시점 npm 최신은 `@docusaurus/core` 3.10.2입니다.

#### MkDocs Material

- **MkDocs**는 Python으로 만든 SSG이고, **Material for MkDocs**는 그 위에 얹는 인기 테마입니다. 설정은 `mkdocs.yml` 하나(YAML 형식)로 합니다.
- 검색·다크 모드·코드 하이라이트 같은 기능이 테마에 잘 갖춰져 있습니다.
- Python과 `pip`(Python 패키지 설치 도구)가 필요합니다. JavaScript를 몰라도 되는 대신, 화면을 크게 바꾸려면 Python 확장이나 테마 덮어쓰기를 배워야 합니다.
- 작성 시점 PyPI 최신은 mkdocs 1.6.1, mkdocs-material 9.8.0입니다.

::: warning 작성 시점의 중요한 공지
Material for MkDocs 공식 사이트에는 **2027-05-05까지 핵심 유지보수만 이어 가고**, 같은 팀이 만든 후속 도구 **Zensical**로 넘어간다는 안내가 올라와 있습니다(작성 시점 기준). 새로 시작한다면 공식 사이트에서 최신 상황을 꼭 확인하세요.
:::

#### Wiki.js

- Node.js로 만든 **동적 위키**입니다. 웹 화면에서 글을 쓰고, 로그인·권한·편집 이력 같은 "진짜 위키" 기능이 있습니다.
- 글과 설정은 **데이터베이스**에 저장됩니다. 공식 문서(2.x 기준)는 PostgreSQL을 강하게 권장하고, MySQL·MariaDB·MS SQL Server·SQLite도 지원한다고 적고 있습니다.
- 즉 **서버 프로그램과 DB가 항상 켜져 있어야** 합니다. 백업도 DB 단위로 해야 합니다.
- 여러 사람이 브라우저에서 바로 고치는 사내 위키에는 아주 잘 맞습니다.

#### GitBook · Notion (SaaS)

- 가입만 하면 바로 쓰는 웹 서비스입니다. 설치·빌드·서버가 전부 필요 없습니다.
- **위지윅**(WYSIWYG, What You See Is What You Get: 보이는 그대로 편집하는 방식) 편집기라 마크다운을 몰라도 됩니다.
- 대신 글이 **서비스 회사의 서버**에 있습니다. 요금제·무료 한도·공개 범위·내보내기 형식이 회사 정책에 따라 바뀝니다(작성 시점 기준, 공식 페이지에서 확인).
- 인터넷이 막힌 사내망 서버에 같은 위키를 설치해 띄우는 용도로는 맞지 않습니다.

#### 정적 HTML 직접 작성

- HTML·CSS 파일을 직접 써서 올립니다. 도구가 없으니 배울 것도, 고장 날 것도 없습니다.
- 하지만 사이드바를 페이지마다 복사해 넣어야 합니다. 레슨 하나를 추가하면 **모든 페이지의 사이드바**를 고쳐야 합니다. 검색·다크 모드·코드 하이라이트도 직접 만들어야 합니다.
- 페이지가 5개 이하인 소개 페이지라면 오히려 가장 단순한 선택입니다.

### 4단계: 한 표로 비교하기

| 후보 | 장점 | 단점 | 어울리는 상황 |
|---|---|---|---|
| VitePress | 빠른 개발 서버, 깔끔한 기본 테마, 내장 로컬 검색, 다크 모드, Vue 컴포넌트 삽입 | Vue 템플릿 문법 때문에 이중 중괄호·꺾쇠가 빌드를 깨뜨리는 함정, 문서 버전 관리 기능은 기본으로 없음 | 한두 사람이 관리하는 학습·기술 문서, 코드 예제가 많은 위키 |
| Docusaurus | 문서 버전 관리·다국어 기본 제공, React 생태계, 블로그 기능 | 검색은 외부 서비스나 플러그인이 필요, 설정·의존성이 상대적으로 큼 | 버전별 제품 문서, React에 익숙한 팀 |
| MkDocs Material | YAML 설정 하나로 시작, 검색·다크 모드 등 기능이 풍부한 테마 | Python 환경 필요, 화면 확장은 Python·테마 지식 필요, 작성 시점 유지보수 종료 예정 공지 | Python을 쓰는 팀의 기술 문서 |
| Wiki.js | 웹에서 바로 편집, 로그인·권한·편집 이력 | 서버·DB 상시 운영, 백업·업데이트 관리, 무료 정적 호스팅에 못 올림 | 여러 사람이 브라우저로 함께 고치는 사내 위키 |
| GitBook · Notion | 설치 없음, 위지윅 편집, 협업 기능 | 요금·정책 의존, 사내망 단독 설치 어려움, 다른 도구로 옮길 때 형식 변환 필요 | 개발자가 아닌 사람도 함께 쓰는 팀 문서 |
| 정적 HTML 직접 | 도구 의존 없음, 구조가 완전히 투명 | 공통 부분(사이드바 등)을 페이지마다 반복, 검색·하이라이트 직접 구현 | 페이지가 몇 장 안 되는 소개 사이트 |

### 5단계: 요구사항으로 걸러 내기

이제 요구사항을 체로 삼아 하나씩 걸러 봅니다. O는 기본으로 충족, △는 추가 작업이나 조건이 필요, X는 맞지 않음입니다.

| 요구사항 | VitePress | Docusaurus | MkDocs Material | Wiki.js | GitBook·Notion | 직접 HTML |
|---|---|---|---|---|---|---|
| 1. 학습 위키 구조 | O | O | O | O | O | △ |
| 2. 코드 예제 | O | O | O | O | △ | △ |
| 3. 무료 공개 | O | O | O | △ 서버 필요 | △ 요금제 | O |
| 4. 사내 서버 | O | O | O | O | X | O |
| 5. 한 사람 관리 | O | O | O | △ DB 관리 | O | △ |
| 6. 검색 | O 내장 | △ 외부/플러그인 | O | O | O | X |
| 7. 다크 모드 | O | O | O | O | △ | X |

::: info 이 표는 "ts-wiki 기준"입니다
같은 도구라도 요구사항이 바뀌면 칸이 바뀝니다. 예를 들어 "여러 명이 브라우저에서 고친다"가 요구사항에 들어가면 Wiki.js·Notion의 칸이 O가 되고, SSG들은 △가 됩니다.
:::

걸러 낸 결과 남는 것은 **SSG 세 개**(VitePress·Docusaurus·MkDocs Material)입니다. 세 도구 모두 요구사항을 거의 다 채우므로, 마지막 결정은 다음 질문으로 갈렸습니다.

1. **검색을 외부 서비스 없이 바로 쓸 수 있나?** → 사내망에서 외부 검색 서비스를 부를 수 없으므로 중요합니다. VitePress와 MkDocs Material은 내장, Docusaurus는 플러그인 추가가 필요합니다.
2. **이미 쓰는 언어 생태계인가?** → ts-wiki는 TypeScript 위키입니다. 독자도 작성자도 Node.js·npm을 이미 설치해 둡니다. Python 환경을 하나 더 두는 것은 "한 사람 관리" 요구사항에 부담입니다.
3. **설정이 작은가?** → VitePress는 설정 파일 하나(`config.mts`)와 테마 파일 하나로 끝났습니다.

이렇게 해서 VitePress가 남았습니다. 자세한 장단점은 [다음 레슨](./02-why-vitepress)에서 봅니다.

## ts-wiki에서는

ts-wiki의 `package.json`은 이 결정을 그대로 보여 줍니다. 의존성(devDependencies)이 세 개뿐입니다.

```json
  "devDependencies": {
    "typescript": "5.6.3",
    "vitepress": "1.6.3",
    "vue": "3.5.13"
  }
```

- DB 드라이버, 로그인 라이브러리, 서버 프레임워크가 하나도 없습니다. 동적 위키(Wiki.js)를 골랐다면 이 자리에 DB와 서버가 들어갔을 것입니다.
- 검색을 위한 외부 서비스 키도 없습니다. `docs/.vitepress/config.mts`의 58~59번째 줄에서 검색을 켭니다.

```ts
    search: {
      provider: 'local',
```

- 다크 모드는 기본 테마에 들어 있어 따로 켤 필요가 없고, 전환 버튼의 글자만 한국어로 바꿨습니다(`darkModeSwitchLabel: '다크 모드'`).
- 빌드 결과는 `docs/.vitepress/dist` 폴더의 HTML 파일 묶음이라, 같은 결과물을 GitHub Pages와 사내 nginx 양쪽에 올립니다(요구사항 3·4번). 이 부분은 [2-5](./05-why-hosting)에서 다룹니다.

### ts-wiki의 결정과 그 대가

| 얻은 것 | 내준 것(대가) |
|---|---|
| 서버·DB 없이 파일만으로 운영 | 웹 화면에서 바로 고칠 수 없음. 글을 고치려면 에디터 + git이 필요 |
| 무료 공개(GitHub Pages)와 사내 서버를 같은 결과물로 | 글을 고칠 때마다 빌드·배포 단계가 필요 |
| 외부 서비스 없는 로컬 검색 | 검색 인덱스가 브라우저로 통째로 내려가므로 문서가 아주 많아지면 무거워짐 |
| Node.js 하나로 모든 도구 통일 | Vue 템플릿 해석 때문에 마크다운 작성 규칙을 지켜야 함 |

## 이럴 땐 다른 걸 고르세요

- **개발자가 아닌 사람 여럿이 매일 고친다** → Wiki.js(사내 설치) 또는 Notion·GitBook(SaaS). git을 배우게 하는 비용이 더 큽니다.
- **v1, v2 문서를 동시에 유지해야 하는 제품 문서** → Docusaurus의 문서 버전 기능이 잘 맞습니다.
- **팀이 Python만 쓰고 Node.js를 설치하기 어렵다** → MkDocs 계열. 다만 작성 시점 Material for MkDocs의 유지보수 일정 공지를 확인하고 후속 도구까지 함께 검토하세요.
- **로그인해야만 볼 수 있어야 한다** → 정적 사이트는 그 자체로 로그인 기능이 없습니다. 동적 위키를 쓰거나, 정적 사이트 앞에 인증 프록시를 두는 별도 설계가 필요합니다.
- **페이지가 3~5장뿐인 소개 사이트** → 정적 HTML 직접 작성이 가장 단순합니다.

## 자주 하는 실수

### 실수 1: 기능 개수로 고르기

- **증상**: 기능이 제일 많은 도구를 골랐는데, 설정 파일이 수백 줄이 되고 업데이트할 때마다 깨집니다.
- **원인**: 요구사항에 없는 기능까지 관리 대상이 되었습니다.
- **해결**: 요구사항 표를 먼저 쓰고, 표에 없는 기능은 점수에 넣지 않습니다.

### 실수 2: SaaS의 무료 한도를 영원하다고 믿기

- **증상**: 1년 뒤 요금제가 바뀌어 공개 페이지에 광고가 붙거나 유료 전환 안내를 받습니다.
- **원인**: 무료 한도·정책은 서비스 회사가 언제든 바꿀 수 있습니다.
- **해결**: 고를 때 **내보내기(export) 형식**을 먼저 확인합니다. 마크다운으로 빼낼 수 있으면 나중에 옮길 수 있습니다. 요금은 작성 시점 기준, 공식 페이지에서 확인합니다.

### 실수 3: 동적 위키를 "설치만 하면 끝"이라고 생각하기

- **증상**: 몇 달 뒤 서버 디스크가 꽉 차거나, DB가 깨졌는데 백업이 없습니다.
- **원인**: 동적 위키는 앱·DB·백업·보안 업데이트까지 운영해야 합니다.
- **해결**: 동적 위키를 고른다면 백업 주기와 복구 연습을 처음부터 계획에 넣습니다. 운영 기본기는 [운영 기본기](../part7-server-learning/06-ops)에서 다룹니다.

### 실수 4: 사내망 조건을 늦게 확인하기

- **증상**: 다 만들고 나서 사내 서버에 올렸더니 검색이 안 됩니다(외부 검색 서비스에 접속 못 함).
- **원인**: 외부 서비스에 기대는 기능은 인터넷이 막힌 곳에서 동작하지 않습니다.
- **해결**: 요구사항에 "인터넷 없이 동작"을 명시하고, 검색·폰트·이미지가 외부 주소를 부르는지 확인합니다.

- B(동적 위키): Wiki.js
- C(SaaS): Notion
- D(직접 작성): 메모장으로 쓴 `index.html`

### 과제 2 ⭐⭐ 내 요구사항 표 만들기

여러분이 만들고 싶은 위키(예: "한빛 카페 직원 매뉴얼")의 요구사항을 5줄 이상 적고, 이 레슨의 "요구사항으로 걸러 내기" 표를 내 요구사항으로 다시 채워 보세요.

::: details 힌트
카페 직원 매뉴얼이라면 "직원(개발자 아님)이 휴대폰으로 고친다", "매장 밖에서는 보이면 안 된다" 같은 요구사항이 나올 수 있습니다. 그러면 SSG보다 Wiki.js나 SaaS의 점수가 올라갑니다. 정답은 하나가 아닙니다. **요구사항이 바뀌면 결론이 바뀐다**는 것을 확인하는 것이 목표입니다.
:::

### 과제 3 ⭐⭐ 가중치 점수표

요구사항마다 중요도(1~3점)를 매기고, O=2, △=1, X=0으로 바꿔 "중요도 × 점수"의 합계를 후보별로 계산해 보세요. ts-wiki 요구사항 기준으로 1등이 VitePress가 나오는지 확인합니다.

::: details 힌트
예를 들어 4번(사내 서버)과 6번(검색)에 3점, 나머지에 2점을 주면 GitBook·Notion은 4번 X 때문에 크게 밀립니다. VitePress와 MkDocs Material은 점수가 비슷하게 나올 수 있는데, 이때 표에 없는 기준("이미 쓰는 언어 생태계")이 결정을 가릅니다. 이런 숨은 기준을 찾아 표에 한 줄 추가하는 것도 좋은 연습입니다.
:::

### 과제 4 ⭐⭐⭐ 공식 문서에서 사실 확인

[참고 자료](../appendix/04-resources)의 공식 문서 링크를 열어 다음을 직접 확인하고, 이 레슨의 표와 다른 점이 있으면 메모하세요.

1. VitePress 로컬 검색은 어떤 라이브러리를 쓰나?
2. Docusaurus 공식 문서가 가장 먼저 안내하는 검색 방식은?
3. Wiki.js 2.x가 권장하는 데이터베이스는?

::: details 정답 보기
1. MiniSearch (VitePress 공식 문서 "Search" 페이지)
2. Algolia DocSearch (Docusaurus 공식 문서 "Search" 페이지)
3. PostgreSQL (Wiki.js 공식 문서 "Requirements" 페이지)

작성 시점 이후 바뀌었을 수 있습니다. 바뀌었다면 공식 문서가 맞습니다.
:::

## 확인 퀴즈

1. 정적 사이트 생성기의 결과물은 무엇이고, 왜 GitHub Pages에 올릴 수 있나요?
2. Wiki.js를 고르면 VitePress에 비해 추가로 운영해야 하는 것 두 가지는?
3. 사내망(인터넷 차단) 요구사항이 있을 때 SaaS가 맞지 않는 이유는?
4. ts-wiki가 Docusaurus 대신 VitePress를 고른 결정적 이유 두 가지는?

::: details 정답 보기
1. HTML·CSS·JS 파일 묶음입니다. 서버가 계산할 일이 없고 파일을 그대로 주기만 하면 되므로, 정적 파일 호스팅인 GitHub Pages에 올릴 수 있습니다.
2. 서버 프로그램(상시 실행)과 데이터베이스(백업 포함)입니다. 로그인 계정 관리도 늘어납니다.
3. 글과 프로그램이 서비스 회사의 서버에 있어서, 인터넷이 막힌 사내 서버에 설치해 띄울 수 없기 때문입니다.
4. 외부 서비스 없는 내장 로컬 검색, 그리고 ts-wiki 작성자·독자가 이미 쓰는 Node.js 생태계 안에서 끝난다는 점(설정도 작음)입니다.
:::

## 정리

- 위키 도구는 **SSG / 동적 위키 / SaaS / 직접 작성** 네 갈래로 나눠 보면 비교가 쉽습니다.
- 비교는 도구가 아니라 **요구사항**에서 시작합니다.
- ts-wiki의 요구사항(무료 공개 + 사내 서버 + 한 사람 관리 + 내장 검색)은 SSG 쪽으로 강하게 기웁니다.
- SSG 세 후보 중에서는 내장 로컬 검색, Node.js 생태계, 작은 설정이 VitePress를 골랐습니다.
- 대가는 "웹에서 바로 편집 불가"와 "빌드·배포 단계가 필요"입니다.
- 버전·요금·정책은 작성 시점(2026-10) 기준이며, 고를 때 공식 페이지에서 다시 확인합니다.
